# 엔진 개발 계획

사용자가 2026-10-02에 지정한 개발 순서다. 규칙의 기준 문서는 [game_rules.md](game_rules.md)다.

## 1단계: C++ 엔진 코어와 순수 MCTS

- 9×9 보드, 선후공, 중앙 중립 돌, 턴, 패스, 종료 상태를 표현한다.
- 돌을 놓는 함수와 합법 착수 판정, 집 판정, 상대 돌 무리의 포위 판정, 즉시 승리와 연속 패스 후 점수 판정을 구현한다.
- 양쪽 동시 포위 시 착수자가 승리하는 우선순위를 지킨다.
- 신경망 없이 무작위 플레이아웃을 사용하는 순수 MCTS를 C++로 구현한다.
- 배열 보드의 규칙 정확성을 먼저 검증하고, 81개 지점을 비트 연산으로 처리하는 Bitboard 최적화를 적용한다. 81비트는 하나의 64비트 정수에 들어가지 않으므로 여러 워드 등 적절한 표현을 선택한다.
- 규칙 문서의 예시와 미확정 사항을 기준으로 검증한다. 일반 바둑의 패, 사활, 포획 후 대국 지속을 임의로 추가하지 않는다.

## 2단계: pybind11 Python 바인딩

- C++ 코어를 pybind11로 감싸 Python에서 `import my_board_engine`으로 호출한다.
- 플랫폼에 맞게 `.pyd` 또는 `.so`를 빌드한다.
- Python에서도 C++과 동일한 상태, 착수, 합법 수, 종료 및 승패 판정을 사용한다.

## 3단계: Python + PyTorch 신경망과 강화학습

- PyTorch 신경망을 구성한다.
- Python 학습 코드가 C++ 엔진을 호출하며 수십만 번의 대국을 생성하고 강화학습을 진행한다.
- 학습된 모델을 저장하고 대국 결과와 성능을 기록한다.
- 입력 표현, 모델 구조, 학습 목표 및 신경망과 MCTS 결합 방식은 이 단계에서 구체화한다.

## 4단계: C++ + LibTorch 자가 대국 최적화

- 저장한 PyTorch 모델을 C++ 코어에서 LibTorch로 직접 로드한다.
- Python을 거치지 않고 C++ 환경에서 신경망 추론, MCTS, 자가 대국을 실행한다.
- 완전한 C++ 학습 루프를 구성하려면 추론뿐 아니라 학습·체크포인트 저장도 이 단계에서 설계한다.

## 성능 목표와 관리

- C++의 실행 속도와 메모리 제어, Bitboard 연산을 활용한다.
- 사용자의 목표는 MCTS 시뮬레이션을 초당 수십만 번 수행하는 것이다. 이는 목표이며 측정된 성능이나 보장치는 아니다.
- 순수 무작위 플레이아웃과 신경망 추론을 포함하는 탐색을 구분하여 측정한다. 하드웨어, 탐색 횟수, 평균 대국 길이 등의 조건을 함께 기록한다.
- GitHub와 연결된 현재 저장소에서 규칙, 코드, 검증 결과, 개발 과정을 관리한다.

## 초기 기록 시점의 저장소 상태

2026-10-02 최초 확인 당시에는 엔진, MCTS, 테스트, 예제 파일 구조와 CMake 설정은 있었으나 C++ 소스·헤더·테스트는 빈 파일이었다. 당시에는 엔진 구현 완료로 표시하지 않았으며, 최초 규칙 문서 저장 작업에서는 엔진 구현이나 빌드 검증을 수행하지 않았다.

## 기본 엔진 구현: 2026-10-02

위 절은 규칙을 처음 저장할 당시의 기록이다. 현재 기본 엔진은 C++20 배열 보드로 구현하며, Bitboard와 순수 MCTS는 다음 단계로 남긴다. 외부 라이브러리 없이 CMake로 코어, 예제, 세 가지 독립 테스트를 빌드한다.

### 공개 API

- 네임스페이스는 `kingdom`, 공개 헤더 위치는 `engine/include/board`다.
- `Board`는 9×9 칸, 상하좌우 이웃, 연결된 돌 무리와 빈 이웃을 표현한다. `to_string()`은 `x/o/v/.`로 보드를 출력한다.
- `State(GameRules rules = {}, std::optional<Position> neutral = Position{4, 4})`로 시작한다. 기본 중립 돌은 중앙이며, 다른 좌표 또는 `std::nullopt`로 숙련자 변형을 설정할 수 있다.
- `State::play(Move::place(row, col))` 또는 `State::play(Move::pass())`로 진행한다. 반환값 `MoveOutcome::accepted()`로 수락 여부를 확인한다. 거부된 착수는 보드와 턴을 바꾸지 않는다.
- API 좌표는 **0부터 시작**한다. 따라서 규칙 문서의 (5행, 5열)은 API의 `{4, 4}`다.
- `State::score()`는 현재 빈 집 칸 수인 `Score{black, white}`를 반환한다. 중립 돌과 집 안에 놓인 자기 돌은 빈칸 점수에 포함하지 않는다.
- `State::result().finished()`로 종료 여부를 확인하고, `State::result()`에서 승자와 종료 사유를 읽는다. 대국 중에는 종료 사유가 `EndReason::None`이다. 연속 패스 판정은 `black - white >= 3`이면 흑 승리, 그 외에는 백 승리다.

### 판정 순서와 집의 소유권

착수 가능 여부를 확인한 뒤 상대 돌의 포획을 먼저 확인한다. 상대를 포획하면 즉시 착수자 승리이며, 자기 돌의 포위 여부가 이를 뒤집지 않는다. 포획되지 않은 경우 자기 돌의 포위 정책과 집 갱신을 적용한다. 완성된 집의 소유권은 상태에 보존하며, 상대의 침투는 금지한다. 빈칸 영역의 경계에 상대 돌이 있거나, 네 가장자리 모두에 닿거나, 소유자의 돌 경계가 없으면 새 집으로 인정하지 않는다.

### 미확정 사항을 위한 구현 옵션

아래 기본값은 개발을 진행하기 위한 **임시 구현 선택**이다. 사용자가 확정한 게임 규칙으로 간주하지 않으며, `GameRules`에서 바꿀 수 있다.

| 옵션 | 기본값 | 구현 동작 |
| --- | --- | --- |
| `suicide_rule` | `SuicideRule::Forbidden` | 상대를 포획하지 못하는 자충수를 거부한다. `SuicideRule::Loses`는 착수를 수락하고 상대 승리로 종료한다. 양쪽 동시 포위 시에는 항상 상대 포획에 따른 착수자 승리가 먼저 적용된다. |
| `allow_own_territory_moves` | `true` | 자기 집 안 착수를 허용한다. 소유권은 유지되지만 돌이 놓인 칸은 더 이상 빈칸 점수에 포함하지 않는다. |
| `allow_single_edge_territory` | `true` | 한 가장자리만 이용하는 집도 허용한다. 네 가장자리 모두를 이용하는 영역은 항상 제외한다. |
| `stones_per_player` | `40` | 각자 돌을 모두 사용하면 패스만 허용한다. 중립 돌 위치 변경과 중립 돌 없는 변형에도 같은 기본값을 적용한다. |

### 빌드와 검증 방법

```sh
cmake -S . -B build
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

`board_test`, `capture_test`, `territory_test`는 보드/턴, 포획 우선순위, 집과 종료 판정을 검증한다. `demo`는 기본 보드 출력, 착수, 연속 패스 종료를 보여준다. 성능 달성 수치는 실제 벤치마크 수행 후 기록한다.

2026-10-02 Windows에서 GCC 16.2.0, CMake 3.29.5, Ninja로 Release 빌드와 예제 실행을 확인했다. CTest의 3개 테스트가 모두 통과했으며, 보드 테스트에는 고정된 20개 시드의 무작위 대국을 끝까지 진행하여 합법 수, 중립 돌 보존, 돌 재고와 종료 상태를 확인하는 통합 검증이 포함된다.
